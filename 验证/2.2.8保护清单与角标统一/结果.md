# 2.2.8 卸载保护改为固定清单、名称列角标统一 —— 实施与验证记录

日期：2026-11-05　基线：2.2.7（已部署）→ 2.2.8

## 起因（用户实测反馈）

1. 概览组件面板里那支天阶显示「此组件是MCE必需依赖，仅可更新」，**卸载被禁用**。用户判断：天阶不可能被 MCE 依赖，也不可能依赖 MCE，「理论上卸载应该畅通无阻，肯定哪里有问题」；并明确——会被 MCE 依赖的就那几个，一只手数得过来、以后也不会变，**除了那几个其余的都应该能顺利卸载**。
2. 版本提示里「有新版本」出现两次。
3. 名称列右侧两个小角标位置、大小、形状都不一致（一个圆形、一个圆角方形），原始设计意图是「贴在名称列右侧右上角一起显示」。

## 一、卸载被禁的真因（已定位并修复）

拦截条件在 `DiagnosticSummary.FromCapability`：`capability.ProtectionPath.Count > 0` → 「MCE 必需依赖」。而 `ProtectionPath` 来自 `ComponentDependencyGraph.GetCapability` 的**硬依赖闭包遍历**（从「提供 MCE GUID 的组件」出发）。

闭包被撑大的机制在收集器：

```
ComponentDependencyCollector.cs:246-247（修复前）
    Edge(owner.Id, "missing:" + requirement.Target, evidence, requirement.Hard);
    foreach (var failure in graph.FailureScopes.Where(f => PluginFileNames.IsAssembly(f.Path)).ToList())
        Edge(owner.Id, failure.Node, "possible provider for unresolved " + requirement.Target + " at " + failure.Path, requirement.Hard);
```

即：**只要某个程序集引用解析不到提供者，就给 MCE 造一条指向「整棵树里每一个读不出来的程序集」的硬边**（注释写作 possible provider）。任何读取失败的模组因此被算成 MCE 的硬依赖 → 进闭包 → 卸载被禁。

本机取证（只读）：

- 扫整个 plugins 树，**只有 `ModConfigEnhance.dll` 自己**在二进制里含有 MCE 的 GUID `com.aiae.modconfigenhance`；即闭包的唯一「种子」就是 MCE 本身。
- 用户截图那支天阶的 `TrueFinalAscent.dll`，该 GUID 在 **UTF-8 与 UTF-16 两种编码下都不存在**，它不该出现在闭包里。
- 该模组在 `plugins/` 下有三份副本（`CptPICHU-TrueFinalAscent/`、`[玩法]真正的最终天阶-TrueFinalAscent/CptPICHU-TrueFinalAscent/`、以及 `3玩法类模组(...)/` 下同名嵌套），包内只有一个 DLL。

结论：不是「该不该保护」的设计问题，而是**闭包被一条伪造的边撑开**；而且它此前是**有意为之**——历史夹具 `验证/InfrastructureTree20261029/Graph/ScopedFix/Checks.cs.txt:84` 明确断言过「unresolved MCE GUID binds damaged candidate and refuses deletion」。本轮按用户要求反转该行为。

## 二、改动

| # | 位置 | 改动 |
|---|---|---|
| 1 | `ComponentDependencyCollector.cs` | 删除伪造的 possible-provider 硬边；未解析的引用只记 `missing:` |
| 2 | `ComponentDependencyGraph.cs` | 新增 `MceRequiredIdentities`（`com.github.PEAKModding.PEAKLib.ModConfig` / `.Core` / `.UI`，即 MCE 唯一硬依赖的宿主与它引用的两个 PEAKLib 程序集）与 `MceRequiredBy`；`GetCapability` 的保护改由该清单判定，**不再用闭包遍历结果**（遍历保留，只喂 unknown/证据诊断） |
| 3 | `DiagnosticSummary.cs` | 受保护组件 `CanUninstall` 改为 true（`CanUninstall \|\| ProtectionPath.Count > 0`）；文案「仅可更新」→「卸载前会再次确认」，词条表 `Loc.InlineTerms.cs` 同步 |
| 4 | `SourceUi.cs` / `ComponentDetailsView.cs` | 新增 `UninstallProtection(key)`；点卸载若命中保护清单，先弹一次确认并列出身份，再由既有的「卸载（安全预览）」核对文件归属与依赖 |
| 5 | `StatusChip.cs`（新） | 角标几何单一来源：8×8 圆角方形、右对齐车道、间距 11、从宿主右上角起算；槽位 0=未读变动、1=有新版本、2 起=待保存/待重启；`Reserve(n)` 供标题预留 |
| 6 | `AvailableUpdateDot.cs` | 有新版角标改走共享槽位与圆角方形；删除自绘圆的 `AvailableUpdateCircle` |
| 7 | `ChangeLedger.cs` | 未读变动角标改走 `StatusChip.UnreadSlot`（原为 24×28 宿主 + 8×8 圆角方形、位置另算） |
| 8 | `ProfilePendingMarkers.cs` | 新增 `firstSlot`（存为 `_firstSlot`）：行内传入即共用同一车道；其余宿主保持原压缩布局 |
| 9 | `OverviewListView.cs` | 行内传 `firstSlot`；标题预留改按本行实际角标数 `StatusChip.Reserve(laneChips)`，不再用固定值 |
| 10 | `OverviewListView.cs` | `UpdateVersionHint` 改为按行拼装，仅当检查消息不是那句重复的「有新版本」时才追加（其余检查消息照旧保留） |

**刻意未改**：`ShopInstallationState.UninstallBlockReason` 里对 `AiAeT-ModConfigEnhance` 与 `BepInEx-BepInExPack*` 的硬拦截保持原样——商店窗口的卸载流程本轮不扩范围；保护清单里的 PEAKLib 三项在概览面板是提示+确认，在商店窗口不拦。

## 三、验证

- 三项构建 0 警告 0 错误（worker net48 / desktop / plugin netstandard2.1）。
- 纯逻辑夹具 `验证/2.2.8保护清单与角标统一/graph/`（链接**真实的** `ComponentDependencyGraph.cs`）：7 项通过。关键一条是**显式造出那条伪造硬边**（`Evidence = "possible provider for unresolved PEAKLib.Core ..."`），断言不相关模组 `ProtectionPath` 为空、`CanUninstall` 为 true、不被拖进验证态；同时断言清单里的两个 PEAKLib 身份仍被钉住。
- 源码契约断言 `source_checks.py`：4 组通过（保护清单、卸载降级为提示、角标统一、文案去重、版本号一致）。
- 完整回归 `验证/统一保存重构/run-regression.py`：23/23 通过。
- 部署 `deployment_20261105_031218`：38 文件、完整备份、逐文件存在与大小核对、部署后清单版本 2.2.8。
- 按用户指定，把 2.2.8 发行镜像进 r2modman 的 `123123` 档案（`BepInEx\plugins\AiAeT-ModConfigEnhance`，原为商店版 **1.0.2**，只有单个 DLL、没有 `Tools/Updater`）；原包目录已备份到 `备份/123123档案_MCE包_复制前_20261105_031908/`。

## 四、未验证 / 待实机

- 角标外观与位置、以及卸载确认弹窗，均需在游戏内看（本轮只做了几何与代码层断言）。
- 档案内的 `mods.yml` 仍记着旧版 1.0.2：本次是手工复制，**不产生** mods.yml 同步记录，所以它不会自动更新 —— 这属预期。真正的同步验证要在该档案里用 MCE **更新另一个模组**，看 `mods.yml` 的版本与条目是否跟着变（本机 r2modman 正在运行时会推迟到下次启动）。
- r2modman 若在启动前按 `mods.yml` 重新同步该包，可能把 MCE 还回 1.0.2；届时重跑 `验证/2.2.8保护清单与角标统一/copy_to_profile.py` 即可。
