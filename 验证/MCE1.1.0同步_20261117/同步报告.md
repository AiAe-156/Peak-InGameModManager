# MCE 1.1.0 改进同步回 IGMM 报告（2026-11-17）

## 最前：导出前提醒「已安装但没记录进方案的模组」（2026-11-18，用户追加）

### 第一步：方案到底记录哪些模组（查代码的结论）
- **不会**把当下所有已安装的模组都记下来。保存方案（`OverviewRepository.SaveProfileDraft` → `OverviewProfileStore.Save`）只写草稿 `_draftMods` 里已有的条目（`DraftCatalogue()` 只由草稿生成）；方案里有、磁盘上已不在的条目保留并标 `installed=false`。停用的模组**只要在草稿里**就记成 `enabled=false`；不在草稿里的，不论启用还是停用都不记。
- 模组进草稿只有这几条路：默认方案第一次建立时（`Initialize` 用 `SnapshotMods` 记下当时全部模组）；在列表里切换启停（`SetPlannedEnabled`）；点行尾「+」（`IncludeModInProfile`，提示「此方案未记录此模组，保持当前状态」）；发布向导或方案页的「收录当前配置」（`CaptureCurrentIntoProfile`，把全部已安装模组按磁盘现状写进当前查看的方案）。
- 所以「已安装但没被方案记录」来自：默认方案建好之后才装的模组——商店安装、更新队列装上的新依赖、手工把文件夹放进 plugins、从缓存恢复、从别的整合包环境拷进来；新建的个人方案之后装的；导入的作者方案里作者那边没有的模组。
- 发布清单按方案里的 GUID 选模组（`PackPublisher.SelectInventory`），这些模组原来不提示、直接漏掉，除非它恰好是已选模组的依赖或同一包目录的成员。原有的 `MissingTargets` 只管反方向（方案里有、磁盘上没有）。
- 本机现状（publish-sim 只读查的，只按 manifest 名对照，仅供参考）：默认方案记了 64 个；名字对不上的插件包 7 个：MonoDetour（多半作为依赖随包）、PeakTextChat、PEAK_Chat_Emojis、FrameDoctor、FootholdForked（停用）、PeakerPlus，以及 IGMM 自己（不算）。准确名单以实机打开发布向导为准。

### 第二步：发布向导里的提醒和解决办法
- 点「下一步：预览并生成」时（`PublishWizard.Preview`），在核对待定依赖、生成文件清单之前先找这类模组；有就弹出提醒，不往下走。
- 范围（`UnrecordedPublication.Find / Eligible`，纯逻辑）：发布清单里的模组（已排除停放文件夹），GUID 不在任何勾选方案里（含 `installed=false` 的旧记录），包目录（或外层嵌套模组的包目录）也不会被打包；只算 plugins / patchers / monomod 里的；IGMM 自己、BepInEx 本体（core、`BepInEx*` GUID）、只有 manifest 的包（`package:`，方案本来就不记录它们）、没有 GUID 的都不算。同一 GUID 装了两份只列一次。
- 提醒窗口：标题写数量；说明「方案只记录收进来的模组，不处理就不会打进整合包」和存入规则；逐行列出名称、版本、启用中 / 已停用，每行一个勾选框（默认全勾，这就是「逐个选择」，工程量小，没另做窗口）。三个按钮：
  - **存入方案并导出**（主按钮）：只存勾选的。先备份，再写入，然后重新验证并继续到文件清单预览，状态栏显示备份位置。
  - **只导出、不存入方案**：再弹一次确认（列出名单，说明本机仍装着、包里没有、方案不变）；确认后照原来的行为导出，同一个向导里不再为这几个提醒，之后新出现的仍提醒。确认窗口按「返回」或 B 回到提醒。
  - **返回**：回发布选项。B / Esc 同样回发布选项（`OverviewUi.SetModalCloseHandler`）。
- **启停怎么写**：本次发布的默认方案照磁盘现状；**勾了多套方案时，其他方案一律记为停用**。理由：其他方案是作者在没有这个模组时定下、测过的组合；以前这个模组根本不在包里，接收方切到那些方案时等于没有它。记成停用，接收方（和作者自己）切到那些方案时与原来一致，不会凭空多出一个在那套方案里没测过的模组。作者想在别的方案里启用，存入后到方案页单独打开即可。
  - 副作用：如果当前**查看**的方案不是本次发布的默认方案（作者在向导里改了默认方案），查看中的方案也记成停用；该模组磁盘上是启用的话，方案页会显示一项待应用的停用。这符合规则，但要实机看一眼会不会让人困惑（实机第 21 条）。

## 导出补查两项结论（2026-11-18，用户追加）

### (A) 整合包导出怎么处理未启用的模组

**代码里实际用到的停用方式（6 种）**
1. **DLL 改名**：IGMM 停用时写 `x.dll.d`；旧版写过 `x.dll.disabled-by-mce`；`.dll` 后面带任何后缀都算停用（`x.dll.old`、`x.dll_off`、别的工具写的 `x.dll.disabled-by-xxx`；最后这种 IGMM 不负责重新启用）。依据：`Updating/PluginFileNames.cs`、`Overview/ModToggleService.AddMove`。
2. **资料包的 manifest 一起改名**：停用一个文件夹里带 `manifest.json` 的模组时，`ModToggleService` 把 `manifest.json` 改成 `manifest.json.old`。纯资源包（没有 DLL）只靠这一个改名。
3. **嵌套模组**：停用外层时内层 DLL 一起改名；「哪些内层原来开着」记在本机方案的 `nestedEnabled` 里，导出时删掉（`OverviewProfileExport.CleanProfile`）。
4. **外部管理器档案**（r2modman / Gale 的 `mods.yml`）：IGMM 在这类档案里运行时，改名的同时更新 `mods.yml`。
5. **IGMM 自己的停用标记 = 方案的启停目标**（`profile.mods[].enabled`）。发布时以**默认方案**为准。
6. **移到 `BepInEx/` 下、`plugins` 之外的文件夹**：IGMM 自己从不往那里移文件（停用代码没有这条路），BepInEx 也不加载它们。但 IGMM 的发布清单会扫描这些文件夹（`OverviewCatalogue.PublicationCache`、`PackPublisher.Inventory`），并把里面以 `.dll` 结尾的程序集当作「启用」。本机游戏目录里现有 14 个这种文件夹，例如 `[依赖]PLL地图与群系库-PLL_Library`、`_旧副本_Foothold-Forked_1.5.1_20261103`、`3玩法类模组(…)`。

**各发布模式的现行行为**（修复后）

| 模式 | 导出时 | 导入 / 解压后 |
|---|---|---|
| 资料包（Data） | 不带模组文件，启停只写在 `profile.json` 的目标里 | 接收方第一次进主菜单时，IGMM 按默认方案改名，提示重启后生效 |
| 商店包（Thunderstore） | 商店模组写成 manifest 依赖；本地附带的资料包按作者磁盘原样复制（不投影）：`.dll.d` 仍是停用，`manifest.json.old` 现在一起带上 | 依赖由模组管理器装成启用；IGMM 第一次进主菜单时按默认方案改名，重启后与作者一致 |
| 完整本地包 / 完整商店包（本地包附「新手版」= 解压即用） | DLL 按默认方案投影成 `.dll` / `.dll.d`；**manifest 现在也一起投影**（`manifest.json` / `.old`）；默认方案里没有目标的模组保持磁盘原名 | BepInEx 只加载 `.dll`，**第一次启动就与作者的默认方案一致**；IGMM 进主菜单登记方案时没有需要改名的文件 |

**混合情况**
- **同一资料包里只停用部分 DLL**：
  - 包里是两个模组且默认方案目标不同：发布被拦下（`ValidateDefaults`，三语提示）。
  - 默认方案里没有目标：按磁盘原样发出，与作者一致。
  - 包里不是模组的库 DLL（没有 BepInPlugin）不参与投影、保持磁盘原名。作者磁盘状态与默认方案不一致时，可能出现「插件停用、库仍启用」，通常无害（未改，见待定 A-2）。
- **同一模组有重复副本**：
  - 两个文件夹里是同一 GUID：发布被拦下，提示确认保留哪份（`SelectInventory`）。这条提示原来只有中文，**已改三语**。
  - 同一位置既有生效原件又有停用副本（如 `x.dll` + `x.dll.d`、`manifest.json` + `manifest.json.old`）：**缺陷，已修**。原来只跳过 `.dll.old`，`.dll.d` 副本会一起打进包；默认方案停用该模组时，投影出的 `x.dll.d` 与副本同名，发布直接失败（「发布文件目标冲突」）。现实里就有这种情况：本机 IGMM 自己的文件夹现在同时有 `InGameModManager.dll` 和 `.dll.d`。现在这类副本一律不随包发出（`PublicationFilePolicy.IsShadowCopy`）。
- **被停用的模组正好是别人的依赖**：
  - 硬依赖（`BepInDependency`）：默认方案停用了被依赖的模组时，发布被拦下（「缺少启用的依赖」）。
  - 商店 manifest 层面的依赖不检查启停（软依赖）。
- **停用资料包的 manifest**：**缺陷，已修**。`manifest.json.old` 原来被发布过滤规则当成垃圾 `.old` 文件丢掉，接收方拿到的停用资料包没有 manifest，失去商店身份（更新检查、依赖识别），以后启用也补不回来。完整模式下还会出现「DLL 按方案投影成启用、manifest 仍是作者磁盘上的停用名」，或者反过来。现在 manifest 会一起发出，并按默认方案投影。
- **`BepInEx/` 下的停放文件夹**：**缺陷，已修（用户 2026-11-18 决定：一律排除）**。原来只要被选中（默认方案里有它的 GUID，或它恰好提供了某个已选模组的商店依赖），发布就把它放进接收方的 `plugins/`。默认方案没有停用它时，它在接收方会被加载，而作者这边从来没加载过；停放的旧副本与 `plugins` 里的同一模组会被判成「重复副本」而拦下发布；依赖校验也会把停放副本当成「启用的依赖」。现在发布清单不再扫描这些文件夹（`PackPublisher.Inventory` 去掉 `PublicationCache`，manifest 扫描跳过停放目录），也不再把它们列为可选附带内容；旧草稿里存过的这类附带路径在三种模式下都跳过（`PublicationFilePolicy.IsParkedBepInExPath / IsParkedGamePath`）。默认方案只引用到停放副本的模组，会按原有逻辑记成「缺少启用模组 / 停用模组未附带」。
- **与「别人拿到包后看到与作者一样的启停」不一致、仍未修的**（写在待定）：
  - **A-2 包内非模组的库 DLL 不投影**：见上。
  - **A-3 商店包（非完整）不投影**：按设计，靠接收方 IGMM 第一次进主菜单时改名并重启；第一次启动会按作者磁盘状态加载一次。
