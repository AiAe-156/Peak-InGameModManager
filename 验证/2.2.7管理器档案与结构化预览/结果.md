# 2.2.7 管理器档案支持与结构化整理预览 —— 实施与验证记录

日期：2026-11-04　基线：2.2.6（已部署）→ 2.2.7

## 起因

用户提问：用雷霆商店或 r2modman 管理模组时，模组不在游戏根目录，而是在
`%APPDATA%\r2modmanPlus-local\PEAK\profiles\<档案>\BepInEx\plugins`；要求查清机制，并确保
导入 / 导出 / 整理等所有文件相关操作都能正常工作。上一轮只读调查（子代理 + 复核）给出的结论是本记录

## 一、基线事实（doorstop 决定，已核对）

- `PreloaderRunner` 用被注入的 preloader 位置推出 BepInEx 根；`Paths.GameRootPath` 由 game exe 位置
  推出。所以在档案布局下：`GameRootPath` = 真实游戏根，`BepInExRootPath` = 档案里的 BepInEx，
  而 **`BepInExRootPath\..` = 档案目录，不是游戏目录**。
- 凡是走 `Paths.*` 的功能本来就正确（配置、启停、概览、方案/翻译、`MCE\` 运行数据、worker 的
  `--root`）。出错的是「把 BepInEx 父目录当游戏根」的那些点。

**刻意没改**：所有 `RejectLinks` 一类的**包含边界**仍是 `--root` 的父目录
（`InstallPlanner`、`PackMaintenance`、`NetworkProbe`、`ShopQueue`、`PackStorage`、`WorkerTargetProtocol`）。
档案目录本来就在游戏目录之外，换成游戏根会把整个安装判成越界。源码断言把这条固定住了。

**刻意没做**：没有让 `ModToggleService` 自动进入「管理器档案模式」。档案布局下 `Paths.PluginPath` 就是
档案的 `plugins`，启停本来就能工作；档案模式是为「游戏根一份安装 + 另有一份档案」设计的，会自动要求
两份路径逐一相等，套到档案布局上反而多出一份同名副本要同步。

## 三、验证

- 三项构建 0 警告 0 错误（worker net48 / desktop / plugin netstandard2.1）。
- 源码契约断言 `source_checks.py`：6 组通过（真实游戏根、边界未动、守卫放行、版本同步接线、
  结构化预览、版本号一致）。
- 完整回归 `验证/统一保存重构/run-regression.py`：23/23 通过。
- **mods.yml 改写回环**（`yaml-roundtrip/`）：把真实的 `123123` 档案 mods.yml（68 条 / 45840 字节）
  复制到夹具里，用**真实的** `ManagerProfileSync.cs`（夹具只补 `BepInEx.Paths` 与 `ManagerLog` 桩，
  并通过 `RunningProbe = () => false` 绕过本机 r2modman 正在运行的推迟分支）跑：
  - 差异**只有** 3 行版本号被改写 + 1 个条目被整段删除；其余 1650 余行逐字节不变。
  - 档案里不存在的键被跳过，不产生任何改动。
  - 第二次运行（记录里的版本已与文件一致、要删的条目已不在）：文件 md5 不变，幂等成立，只留下 1 份备份。
  - 曾先用 YamlDotNet 的 `yaml.Save` 整档回写，实测会把全部 68 条的缩进与折叠长行重排
    （1689 行 → 1632 行、45840 → 47060 字节），语义等价但对管理器的文件改动面过大，故改为行级改写。

## 四、未验证 / 待实机

- 本机当前**不是**从 r2modman 加载的（游戏根有自己的 doorstop，60 个插件都来自游戏根的
  `BepInEx\plugins`；两个档案时间戳停在 11-03 与 2025-12）。所以本轮改动在本机现状下**不触发**，
  需要在真的用 r2modman/雷霆商店启动时验收：
  - 更新一个模组后，下次启动看 `mods.yml` 的版本是否被同步、日志里是否有「管理器档案已同步」；
  - 卸载一个模组后，看 `mods.yml` 里对应条目是否消失；
  - 整理预览确认窗口的树是否按语言正确渲染、包目录名是否不再带 `--哈希`。
- 本机 r2modman 正在运行（4 个进程），同步会被推迟 —— 这是设计行为，但也意味着实机验收时
  需要先关掉管理器再看日志。
- `PackPublisher` 的导出校验（「输出目录不能位于游戏安装目录内」）在档案布局下的实际拦截效果未实机验证。

## 五、运行时验收（沙盒，2026-11-04 补做）

在临时目录伪造一套档案布局（`<沙盒>\profile\{mods.yml, doorstop_config.ini, BepInEx\{plugins, MCE\tools\...}}`
+ `<沙盒>\game\PEAK_Data\Managed`），用**已部署的真实 worker** 直接跑：

- `--root <沙盒>\profile\BepInEx --game-root <沙盒>\game --protocol 2 --once`
  → **exit 0、stdout/stderr 皆空**，并在档案的 `BepInEx\MCE\` 下正常建立
  `queue.json / commands / processed / logs / maintenance / worker.lock`。
  与旧行为对照：同一命令行用**旧版缓存 worker** 会立刻抛
  `此目录由管理器维护，首版仅更新纯本地安装。`（`Files.ValidateRoot`）。这是本次主线修复的运行时证据。
- 跨序列化器读回：worker 端用 `System.Text.Json`（PascalCase）写出 `manager-sync.json`，插件端用
  Newtonsoft 读回，改写结果与两端口径一致的用例**完全相同**（差异仍只有 3 行版本 + 1 个条目整段删除）。

### 顺带查清的两件事（不改动）

- `src/Updating/UpdateMessageCatalog.cs:17` 仍留着 `manager-maintained-root` 词条（中英繁三语），
  但已无任何代码引用它 —— 抛错删除后它成了死数据。**注意**：worker 是 .NET 程序集，字符串以 UTF-16
  存储，判断某句文案是否还在二进制里必须用 UTF-16 编码去搜；用 ASCII/UTF-8 grep 中文串会一概「搜不到」，
  本次就先因此误判过一次。
- `<游戏>\BepInEx\MCE\tools\` 下留着 4 份历史 `p2-*` 助手缓存（都不含 `--game-root`，属旧版）。
  新部署不会刷新它们，只新增一份；插件启动时按来源重新缓存（`WorkerProtocol.PrepareTools`），
  旧缓存由 worker 的磁盘回收负责。本次沙盒最初就是错用了其中一份旧缓存，才看到旧守卫 —— 记录以免再踩。

- 从 csproj 读 `DeployDir` 的自建脚本必须做 **XML 反转义**：该值是
  `...\plugins\0核心&amp;基础模组\...`，直接用会得到字面量 `&amp;` 而报「现装目录不存在」。
  本次第一版 `deploy.py` 就因此中止（尚未写任何文件、未创建 result.json），补 `html.unescape` 后正常。
