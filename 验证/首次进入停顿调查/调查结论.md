## 结论（按对「刷十几个停一下」的贡献排序）

### 1. 同一份列表在首次进入后被**整页重建了不止一次**

`MethodProfile` 里 `BuildModLayers` 的调用次数（每行 5–6 次 MoveNext）：

| 时刻 | 累计调用 | 增量 | 约合行数 |
|---|---|---|---|
| 16:41:34 | 402 | 402 | ≈ 67 行，第 1 遍 |
| 16:41:50 | 804 | +402 | 第 2 遍 |
| 16:42:50 | 1206 | +402 | 第 3 遍 |
| 16:43:20 | 2412 | +1206 | 3 遍 |
| 16:45:05 | 2892 | +480 | 第 7 遍 |

首次进入后约 16 秒，整份列表又从头建了一遍（16:41:34 → 16:41:50）。用户看到的是：列表逐行出现，出到一半停下，然后又重新出一遍。

`Render()` 每次都会清空全部行并重建。首次进入这段时间里，**真正把列表推倒重来的是这一处**：

- **`OverviewPage.PollUpdates` 第一次轮询就调 `_list.Reload()`**（`OverviewPage.Updates.cs:149-151`）。它把「更新队列里历史任务的指纹」和 `_updateInventoryKey` 比较，而这个字段初值是空串。现场队列里有 27 条历史任务（completed 21、superseded 4、rolled-back 2），指纹不可能是空串，所以**每次进程首次进概览，进页后 0.2 秒内必定 Reload 一次**。Reload 会重新扫描全部程序集、重跑组件扫描（`RefreshInfrastructure(true)`），扫描回来后再整页 Render。这个检查本来是为了「更新任务完成后刷新列表」，但第一次比较时没有基准，于是被当成了「有新完成的任务」。
- 时间吻合：第一遍在 16:41:26–34 建完（402 次 MoveNext），第二遍 16:41:34–50（+402）。

其他可能触发、但这次没有造成整页重建的：

- `FlushInfrastructureRedraw`：`Render()` 在 `_infrastructureLoading` 期间会直接返回，所以首次打开时，模组行要等组件扫描回来才一次性建出来，**本身不会多建一遍**。只是 Reload 又把组件扫描重启了一次。
- `RefreshSharedUpdateCache`：16:47:23 自动更新检查写入缓存（`updates.json` 里 51 条都是 08:47:23 UTC），走的是 `RefreshUpdateRows`，只重建数据变了的行。
- 宽度变化（`Math.Abs(width - _lastWidth) > 2`）：`OverviewPage.Update` 那 153 ms 是 2.2.6 登记过的 `RefreshHeader`，不是列表重建。

### 2. 每帧建行的预算形同虚设：一帧最多建 16 段，但单段就可能 100+ ms

- `RowBuildBudget(maxSteps: 16)`：每帧 2 ms 或 16 步就停，但只在**两段之间**检查。**第一段必定放行**（`_count>0` 才判断超时），所以一段 129 ms 的工作会整块落在一帧里。
- 129 ms 那一段在 `BuildModLayers` 第一个 `yield` 之前，也就是：标题、版本、作者、简介四个 TMP 文本、来源标签、依赖悬停绑定，外加 `ReadableName` 和 `PlaceClipped` 里的 `GetPreferredValues` / `ForceMeshUpdate`。第一次遇到某种字体或字形时，TMP 要生成字形图集（中日韩字形走回退字体），这在冷启动时最贵。所以停顿集中在**前十几行**：遇到新字的那一行特别慢，之后就快了。
- `OverviewListPump.Update` self 119 / 245 ms：pump 队列里的 action 是逐个跑的，4 ms 的预算同样只在两个 action 之间检查。被重建（第 1 条）放进队列的整块 `Render()` 本身就是一个 action，等于把整页清空、重排、建骨架都放在这一帧里。

### 3. 「无法解释」帧：主线程只有几毫秒，却卡了 100–300 ms

- 整个会话有 152 帧，中位数 121 ms，只有 1 帧带 GC。这类帧在 16:41:20–16:43:20 和 16:47:20–16:48:00 最密集，**正好是列表在建行或重建的时段**；中间空闲的几分钟几乎没有。
- 主线程计数器低、帧却很长，说明时间花在 Present/垂直同步等待或渲染提交上：Canvas 网格突然大量增加（一次建 60+ 行、每行十几个 Graphic），下一帧要重新合批、上传。FrameDoctor 的结论也是「优先怀疑 present/vsync 或资源加载」。
- 这部分不在任何 C# 方法里，只能靠**减少同一时间新增的 Graphic 数量**来缓解。第 1 条修好以后，首次进入时建行的总量减半，这类帧预计也会相应减少（未实测）。

### 4. 其他点名但不属于「刷十几个停一下」的

- `LogWindow.Update` 232 ms：打开日志窗口时第一次 Refilter，要对全部记录逐条测量换行宽度。打开日志才会出现。
- `ComponentDetailsRefresh.Update` 132 / 135 ms：打开组件详情时，两次都是 GC。
- `OverviewMaintenance.LateUpdate` 124–262 ms：10 分钟里出现 6 次，**每次都是 GC 主导**（GC 115–249 ms）。巡检本身已经在 2.2.3 改成按预算分帧，这里是整个进程的垃圾在这一帧被回收。
- 进入设置页时 PEAKLib.ModConfig `builderDelegate` 一次 1271 ms：MCE 挂了 postfix，但耗时没法拆给本体或补丁，需要另外对照。

## 修复方案（待拍板）

| # | 改法 | 影响 | 风险 |
|---|---|---|---|
| A | **首次轮询只记基准，不 Reload**：`_updateInventoryKey` 在进页（`PrepareCachedPage`）时就写成当前指纹；之后只有指纹真变了（有任务新完成）才 Reload | 去掉首次进入的整页第 2 遍，「出到一半重来」消失 | 很小：进页时列表本来就是按当前磁盘重新扫的，记基准不会漏掉任何已完成的任务 |
| B | **Reload 回来时不整页重建**：复用 2.3.6 的停放/搬位，已经建好且数据没变的模组行只挪位置 | 以后更新完成、改组件等触发的 Reload 也不再整页闪一遍 | 中：Reload 会重建 `OverviewMod` 对象，复用条件要从「同一个对象」放宽到「同一 ID 且数据戳一致」，并且要把行内的闭包换成新对象。值得做，但要单独回归 |
| C | **单段预算真生效**：`RowBuildBudget` 的「第一段必放行」改成每帧至少放行一段，但该段之后立即让出；pump 里的 Render 拆出去，不和其他 action 挤在同一帧 | 防止一帧里连续跑几段重活 | 小 |
| D | **字形预热**：进入概览前，在不可见的 TMP 上把列表要用的全部文字（名称、译名、作者、简介）先 `ForceMeshUpdate` 一遍，分帧做，每帧限时 | 把「遇到新字就卡」挪到页面出现之前，前十几行不再一顿一顿 | 会多出一点后台时间；要控制在每帧 ≤ 2 ms，才不会把卡顿挪到主菜单 |
| E | **单行内的第一段再拆细**：标题、版本、作者、简介各成一段 | 单段 129 ms 降到 30–40 ms 量级 | 改的是 2.0.x 定下的层级结构，需要回归 |
| F | 日志窗口首次 Refilter 分帧 | 只影响打开日志时 | 和本问题无关，可以另做 |

建议**先做 A**：改一行就能去掉首次进入时最主要的那次重来，最容易验证。然后在实机上复测：如果前十几行仍然一顿一顿，再做 D（必要时加 E）。B 和 C 是通用加固，可以随后单独做。
