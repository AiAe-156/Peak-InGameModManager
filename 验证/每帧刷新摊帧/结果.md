# 每帧刷新摊帧（2.2.3）

## 为什么改

用户实测 MCE 概览界面持续卡顿、「低帧瞬间掉到个位数」。游戏根目录 `output_log.txt` 里 FrameDoctor + TrueFinalAscent 的 hitch 记录已经把责任落到具体方法：

| 罪魁方法 | ≥100ms 次数 | 实测单帧 |
|---|---|---|
| `Overview.OverviewMaintenance.LateUpdate` | 20 | 120 ~ 210 ms |
| `Overview.OverviewPage.Update` | 6 | ≥100 ms |
| `Overview.AutomaticUpdateChecks.Update` | 5 | 1208 / 1220 / 1230 / 1315 / 1460 ms（均带 GC） |
| `Overview.LogWindow.Update` | 3 | 265 / 323 / 367 ms |
| `Overview.OverviewEntry.Update` | 1 | 441 ms |

全日志 99 条掉帧里 53 条点名 ModConfigEnhance。本轮**只修每帧刷新这一条**（`OverviewMaintenance` 及其驱动的待应用状态）。

## 根因（逐行核实）

1. `OverviewMaintenance.LateUpdate` 每 0.2 秒把**全部** `Checks` 重新标脏，每 2 秒把**全部** `EventChecks` 重新标脏——后者条件里的 `Time.unscaledTime>=_eventNext` 本身就构成定时器，与主题/语言是否真变化无关。
2. 同一帧内把当轮所有 `Dirty` 项 `refresh()` 跑完，**没有时间预算、没有游标**。注册量随已装模组数增长（整表常驻，50+ 行 × 每行约十来个绑定 ≈ 500+ 项），单项虽各自带早退，但 500 × 约 0.25ms ≈ 120~210ms。
3. 主要分配源：`ProfilePendingMarkers.Refresh` 在早退之前无条件调 `_state()` → `OverviewRepository.GetPendingState()`（`PluginInfos.ToDictionary`、`KnownLoadedEntries`、`ReadOfflineValues`、`IntroductionHash`、逐参数/逐模组 new 对象、每分组 JSON 序列化）。它自带 0.2 秒 memo，与巡检**同周期**，于是每轮都正好撞上过期、整份投影重建一次并触发 GC。列表侧 `MarkerState()` 的 0.19 秒 memo 同理。

## 改了什么

| 文件 | 改动 |
|---|---|
| `src/Overview/OverviewMaintenance.cs` | 一轮巡检改为「固定游标 + 复用 `RowBuildBudget`（每帧约 2ms、最多 64 步）」；一轮未跑完不开启下一轮；显式 `Mark` 走独立优先队列；轮内已不需要刷新的条目**不计预算**（否则空转会吃掉预算、错过整点）；去掉每帧 `Dirty.Keys` 全量拷贝；`AddToRound` 用引用判空以便销毁的控件仍能进轮被清理 |
| `src/Overview/OverviewRepository.Pending.cs` | 新增 `PendingViewRevision`；`InvalidatePendingView()` 递增版本号并置 `OverviewMaintenance.PendingInvalidated`（让巡检立即开新一轮）；兜底窗口 0.2 秒 → 2 秒（真实改动全靠既有的 `InvalidatePendingView` 立即失效，`introductionDirty` 仍是 memo 键之一，介绍文档改动照旧即时生效） |
| `src/Overview/OverviewListView.cs` | `MarkerState()` 由 0.19 秒计时缓存改为跟随 `_repo.PendingViewRevision`，另留 2 秒兜底 |

版本号 2.2.2 → 2.2.3，同步 7 处：`src/Plugin.cs`、`manifest.json`、`ModConfigEnhance.csproj`、`Desktop/MCE.Desktop.csproj`、`Updater/MCE.UpdateWorker.csproj`、`README.md`（标题）、`README.md`（章节标题，另加正文）。

## 验证

### 纯逻辑检查 `验证/每帧刷新摊帧/`（编译真实源码 + Unity 桩，500 个控件、104 帧 @60fps）

```
PASS  单帧刷新数受预算约束  (max=64 limit=64)
PASS  一轮不会挤在单帧  (max=64 owners=500)
PASS  没有任何控件被跳过  (min=8)
PASS  每个控件每轮至多被刷新一次（次数差 ≤1）  (distinct=8,9)
PASS  刷新次数等于完成的轮数（轮不重叠）  (perOwner=8~9 ticks=9)
PASS  显式 Mark 当帧即生效  (delta=1)
PASS  轮进行中不重复刷新同一控件  (refreshes=320 max=1)
PASS  轮进行中不开启新的一轮  (refreshes=320 budget=320)
PASS  无可见控件时不刷新  (refreshes=0)
```

逐帧轨迹 `64,64,64,64,64,64,64,52,0,0,0,0` 循环：每轮 8 帧（7×64+52=500）走完，整点间隔 12 帧，不再有任何一帧吞下整表。

**过程中测试抓到并修掉一个真缺陷**：第一版把「已经通过显式队列刷过的控件」仍留在巡检轮里，空转的游标步数照样吃预算，导致轮被拖长、错过整点、各控件刷新次数出现 7/8 不一致。现在空转不计预算，差异只剩测试自身用 `帧号/60` 造时间时的浮点取整（8 与 9 即「最后一轮被窗口截断」），属测试假象，已在断言里如实体现而不是掩盖。

- `AutomaticUpdateChecks.Update` 单帧 1.2~1.5 秒是「主线程全量扫描」，与「每帧刷新」是两件事，本轮**未修**。

- 「按分组整理预览」无进度输出、预览阶段对全部文件做 SHA256，本轮**未修**。
- `plugins\0核心&基础模组\[界面]ModConfig增强-ModConfigEnhance\` 是停用副本（插件已改名 `ModConfigEnhance.dll1`，另带一份 74MB 的旧 worker exe）——删除/迁移属破坏性操作，**未动**。
