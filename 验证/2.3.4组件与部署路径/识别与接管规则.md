# 模组识别与接管规则（2026-11-09 与用户对齐）

两步：**① 识别**——plugins、patchers、core 以及缓存区里所有模组都要在概览里出现，BepInEx 本体除外；**② 接管**——识别出来以后，MCE 能对它做哪些操作。

## ① 识别
| 形态 | 现状 | 目标 |
|---|---|---|
| 文件夹里有 manifest 和插件 DLL | 能识别（55 个） | 不变 |
| 文件夹里有插件 DLL，没有 manifest（本地包） | 能识别（2 个） | 不变 |
| plugins 根目录下散放的单个 DLL | 能识别（现场 0 个） | 加「散放」角标 |
| 插件 DLL 带 `.dll.<后缀>`（停用） | 能识别（3 个） | 不变 |
| DLL 名是 `xxx.dll` 后面直接接字符（如 `ModConfigEnhance.dll1`） | **识别不到** | **用户拍板：`.dll` 后面带任何字符都算停用副本**；MCE 自己停用时仍写 `.d` |
| 只有 manifest、没有 DLL（资源包：Aeralis 两个） | **识别不到** | **用户拍板：作为「资源包」正常显示**，既不算停用，也不算缺失 |
| manifest 文件夹的 DLL 在别处（MonoDetour：说明文件在文件夹里，DLL 平铺在 core/patchers 根下） | 2.3.3 起按包自带的文件名补认 | 归并成同一行，不再单独为文件夹显示一行 |
| manifest 加上只剩库 DLL（MCE 2.0.0 的旧停用副本） | 识别不到 | 「.dll 后带字符」那条做完后，会显示为已停用的副本 |

## ② 接管（用户拍板：全部可接管，用提示代替拦截）
- 普通模组、散放 DLL、资源包、外部工具停用的模组：启停、卸载、分组、整理都可以做。散放 DLL 第一次整理时会被收进一个以它命名的文件夹。外部工具停用的模组照旧提示「请用原工具恢复」。
- **基础组件（core/patchers）**（用户指定）：
  - MCE 必需依赖（固定清单里的 3 个）以外，都允许卸载、删除、重命名等操作。
  - 不能改分组，固定在「基础组件」里。
  - 不参与目录整理。现状已经如此，规划器只处理 plugins。
  - 待确认：「重命名」是不是指启停（改后缀）。目前组件只有卸载，没有启停。

## MonoDetour 以前为什么能识别、后来为什么识别不到
- 2026-11-02 14:12 第一次装 MonoDetour 时，DLL 就装在 `core/` 根下，说明文件放在 `plugins/MonoDetour-MonoDetour/`。
- 当天某个时候 `core/MonoDetour-MonoDetour/` 文件夹里也有了一份同名 DLL，和根目录的重复。这份可能来自管理器或手动复制。那段时间扫描能在文件夹里找到 DLL，所以能识别。
- 21:47 与 22:02 两次「同版本重装」，按「core/patchers 里同名程序集会被重复加载」的规则，把文件夹里那份归档进 `MCE/backups`（`9f0964f3`、`8a43e351`），只留下根目录那份。从这之后文件夹里没有 DLL，扫描就丢掉了这两个包。
- 文件和加载从头到尾都正常（`LogOutput.log`：`0.com.github.MonoDetour.BepInEx.5 0.7.17.0`）。
